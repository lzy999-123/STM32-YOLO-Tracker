## 1. 本次目标与完成情况

用户要求修复只看画面时也存在的间歇停顿，确认手机热点、板子与电脑距离在一米内；现阶段没有可用于对照的网线。热点手机为红米 K70E，用户确认没有开启省电模式。承接 [前次诊断](2026-10-10-08-video-stutter-link-diagnosis.md)，此次实施修复并记录失败的试验。

已经实施并验证的改动：

- RTSP 优先 UDP，打开失败再回退 TCP；读取超时为 1000 毫秒，无帧巡检为 1500 毫秒。读取失败释放原连接，以会话 ID 保护有限重连；关闭或切流取消旧重连，连续收到合格画面后才重置预算。
- 视频异常时停止跟踪并清除前一会话的当前帧和待处理帧，避免重连握手期间使用旧图像。
- 板端视频套接字设置 AF41，控制 UDP 设置 CS7；Windows 控制通道通过 qWave 配置发送优先级。保持原生 1280×720、30 FPS、GOP15、2048 kbps、默认垂直翻转和左上角时间。
- 控制与发现可共用一个 Python 进程，保留原发现协议及签名，并逐轮限制发现请求处理量。
- 已修复发现启动脚本的时序缺陷：控制启动脚本返回时 Python 可能尚未绑定发现端口；发现脚本现在有界等待注册，共用服务存在时不再驻留第二个 Python。
- 经用户授权，将 Intel AX201 驱动由 23.160.0.4 升级至 24.70.0.3；备份旧驱动及试验前参数，安装返回 0，无强制重启要求。

**尚未达到“卡顿消除”的验收目标。** 两分钟接近 30 FPS 的窗口之后，正式程序仍出现长断流；新版驱动仍记录 5002/5005 内部错误。关闭数据包合并/MIMO 省电，以及暂用 802.11g，都没有可靠消除长空档，已恢复这些无效参数试验。最终稳定性和重启后的完整验收仍待完成。

## 2. 本次学到的知识

- 平均帧率与画面连续性是不同指标 → 29.95 FPS 的窗口仍有 524.56 毫秒无帧间隔 → 同时记录最大空档、100/200 毫秒以上空档数、绘制节奏及控制状态。
- UDP 与 TCP 各有实际限制 → UDP 有丢包与解码损坏；本设备 TCP 对照有 5.41 秒停顿 → 根据实测选择传输，保留打开失败回退，不能将切换 UDP 写成无线问题已解决。
- 连接恢复需要会话保护 → 旧 worker、关闭操作、延迟重连可能交错 → 对通知和恢复都核对当前会话，避免关闭后自动重开。
- Python 解释器常驻开销会影响小内存板子 → 内核可管理内存约 33 MB，重复发现解释器常驻约数 MB → 优先复用现有事件循环，而非增加一个常驻进程。
- 启动命令完成不等于子进程服务就绪 → 控制脚本的后台 Python 与下一发现脚本存在启动竞争 → 以实际端口注册标记与进程身份判断就绪，并给出有界等待。
- 参数设置成功不等于问题改善 → 网卡新驱动、节能设置和 802.11g 试验都曾显示成功，但后续仍有长空档 → 无效试验恢复原值，保留失败证据。
- 无线重连可能选择其他已保存网络 → 2026-10-11 恢复参数后电脑取得另一网段地址 → 测量前重新核对接口地址、路由和设备可达性；不把离开热点后的超时当原链路丢包。

## 3. 遇到的问题与解决过程

| 现象 | 证据与原因 | 处理方法 | 结果 |
| --- | --- | --- | --- |
| TCP 显著停顿、解码损坏 | 原始 TCP 约 15.30 FPS、最大 7.34 秒；新驱动 TCP 对照 22.15 FPS、最大 5.41 秒 | UDP 优先并保留 TCP 打开回退 | 多个 UDP 窗口改善；无线停顿仍存在 |

| 板端摄像头进程消失 | 10 日两次 OOM；第二次内核在启动时间 8879.607 秒杀死 rkipc | 共用控制/发现解释器，恢复摄像头 | 后续 120 秒窗口无新增 OOM；这不代表开机全过程通过 |
| 正式程序后续再次失败 | 10 日正式日志有 H.264 错误、UDP/TCP 打开超时，重连预算耗尽及控制在线状态波动 | 重新检查当前网卡事件和板端服务 | 否定之前短窗口足以证明稳定的结论；进程后来不存在，未发现应用崩溃事件，不能断言崩溃 |
| 升级后仍有网卡内部错误 | Netwtw14 在 10 日 22:59:35、23:10:37，以及 11 日 13:18:43 记录 5002/5005 | 新驱动上重试关闭合并与 MIMO 省电 | 未解决；恢复两项原值 |
| 802.11g 对照仍停顿 | 11 日 120 秒有 28.92 FPS、最大间隔 1013.42 毫秒、114 次超过 200 毫秒 | 以 54 Mbps 的 802.11g 做有界对照 | 控制在线，但画面连续性未改善；恢复 802.11n/ac/ax 原配置 |
| 11 日本次开机又无视频 | 新 boot ID；内核在 52.401 秒 OOM 杀掉 rkipc。重复发现 Python 已启动且因 UDP 端口占用反复报错，启动期还有 rk_net_proc 暂态进程 | 发现脚本等待共用端口注册，在守护循环也检查共用服务；停止重复进程并恢复摄像头 | 快速依次启动控制/发现后仅一个 Python，摄像头存活；没有授权主动重启板子验证完整开机 |

## 5. 以后做项目要注意什么

1. 需要故障后的长期验证：一次两分钟通过不能覆盖之后出现的驱动错误或 OOM。
2. 服务自启同时核对进程数量、端口实际所有者、内存峰值与服务就绪时序；不能仅执行一次 `start` 就认为重启后可靠。
3. 硬件试验按阶段保留原值，记录当前驱动和接口身份，失败的改动恢复。网卡重连后重新核对网络，避免测试另一条链路。
4. 低内存设备不为了采样再加常驻 Python，也不通过显示队列隐藏无线空档。
5. 旧图像和迟到信号必须在关闭、切流、断流时作废；控制优先级不能替代失联保护。
