## 2. 本次学到的知识

- 模态窗口仍处理事件 → `QMessageBox::warning()`进入嵌套事件循环，遥测和视频仍会回调 → 弹窗前必须释放非递归锁；不能把“等待用户确认”误认为全部回调已暂停。
- 后台计算不能靠GUI补做状态处理 → CSRT在后台，但YOLO回调原来排队到GUI后等待相同状态锁并进行候选外观校验 → 引擎数据处理可在受锁保护的工作线程完成，界面只接收结果。
- DirectConnection会改变锁的实际执行位置 → 初始化结果原来在持有Dnn输入锁时发出 → 先释放输入锁，再通知会获取引擎状态锁的回调，保持state→input的顺序。
- 测试要证明正确触发条件 → 首版合成视频没有更新CameraManager的到帧时间，导致巡检先关闭摄像头 → 更新模拟到帧时间，并在停止控制回包之前断言仍在跟踪，确保实际验证的是控制超时停止。
- 部署与算法验证分开 → 测试程序最初缺Qt Test DLL和offscreen插件路径 → 借用已部署运行库并明确插件路径后，才获得有效行为测试结果；启动失败不能当作线程回归证据。

## 3. 遇到的问题与解决过程

| 现象 | 证据与原因 | 处理方法 | 结果 |

| 提示框出现后GUI存在永久死锁路径 | 已确认：选择目标和开始跟踪均持有非递归m_modeMutex调用warning；提示框期间tryLock失败。遥测/视频回调同线程再次读模式会等待自身持锁 | 只在短锁区复制模式值，解锁后再弹框 | 两个入口都可在提示框仍显示时处理真实模拟UDP遥测，并在关闭后验证新模式 |

| 修改回调线程会引入锁反转 | 已确认：初始化dnnTrackedResult持有m_mutex发出，发信号时同线程tryLock失败；processFrame和stopTracking使用state→input顺序 | 锁区内完成状态更新并复制结果，离开锁区后再发成功或失败结果 | 实际YOLO26n推理初始化信号检查通过 |
| 现场视频仍有接收问题 | 观察：修复版实际RTSP播放仍出现读取超时和H.264解码告警 | 检查窗口响应，保留日志 | 不将上游视频问题混写成已由GUI锁修复解决 |

## 5. 以后做项目要注意什么

- 持锁区只处理短状态操作，不在其中弹模态框、等待用户或处理嵌套事件循环。
- 给复杂算法安排后台线程后，继续检查其结果回调的线程归属和共享锁；不能只看计算函数本身在哪个线程。
- 改连接类型前列出所有锁的次序，检查每一个发信号位置；默认排队曾隐藏的锁反转可能在直接回调后变成硬死锁。
- QWidget操作保持在GUI线程，引擎的工作线程通知通过Qt自动排队到MainWindow。
- 定时器测试同时模拟帧到达时间和控制心跳，防止其他巡检提前终止测试而产生假通过。
