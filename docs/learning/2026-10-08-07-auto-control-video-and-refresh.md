## 2. 本次学到的知识

- **控制连接与视频订阅要分开** → 原代码发现设备后直接打开相机，视频关闭时又断开控制 → 设备通信需要在用户不开画面时保持在线时，应分别管理设备地址、控制会话和视频请求。
- **控件存在不代表能被点击** → 地址标签后创建，原来在 `(390,50)` 占 400×16，覆盖刷新按钮 `(590,40)` 的中部 → 检查实际几何位置与命中控件，比只检查槽函数更有效。
- **UDP 重试必须幂等** → 首次 welcome 丢失后应允许同一活跃会话重发 hello；只有关闭或超时的会话才能封存 → 握手不能把正常重试当旧会话重放。
- **拒绝旧会话需要配套新会话恢复** → 板端封存超时会话后，电脑不能永远重试同一个已过期标识 → 超时后生成新会话，同时不重放旧运动指令或坐标。
- **连接成功不等于有视频帧** → 故障期间 RTSP 端口监听、部分握手成功，但独立解码连续约 19 秒收不到帧 → 同时检查网络、RTSP 与实际解码结果。

## 3. 遇到的问题与解决过程

| 现象 | 证据与原因 | 处理方法 | 结果 |
| --- | --- | --- | --- |
| 视频打不开 | 观察：首次独立 TCP 取流 open 成功、0 帧、8 次读取失败；UDP 原始视频在约 8 秒中仅收到 33 个帧时间戳，检测到 5 个缺包 | 先备份板端编码配置，重启视频服务，重连 Wi-Fi；仍异常后重启板子，用户将板子移到热点旁 | 最终 Qt 实板收到原生 1280×720，连续解码约 30 FPS；最初触发因素尚未定位 |
| 网络时好时坏 | 已确认：一轮到板子的 1400 字节 ping 丢 3/4，而同类到热点测试 6/6 成功；移近后另一轮到板子 8/8 成功 | 进行同一阶段链路对照并记录恢复操作 | 确认曾有明显板子方向通信异常，不把信号显示或短暂成功当永久稳定证据 |
| 刷新点击没有反馈 | 已确认：标签与按钮几何重叠；原槽函数在发现进行中直接返回，关闭视频时刷新反而请求开视频 | 消除遮挡；明确进度和完成提示，刷新只处理设备连接 | Qt 命中控件检查及 Windows 实际鼠标点击通过 |
| 视频状态影响控制 | 已确认：旧代码在 Idle、Closing、Error 中断开控制 | 删除视频状态中的控制断开，保留停止跟踪；用独立视频请求决定是否开流 | 模拟与实板均验证关闭视频后控制仍在线 |
| Wi-Fi 恢复后控制重试仍不成功 | 已确认：Bridge.reply 每次回复把当前会话加入 retired，后续同会话 hello 被拒；新测试在修复前失败 | 改为 Bridge.release 时封存会话；电脑握手沉默 1.5 秒后更换会话 | 修复后 11 项 Python 协议测试通过；已部署真实板端服务 |
| 实板测试早期失败 | 观察：前两轮自动控制在线，但 TCP/UDP 视频失败；不能当成工作流已完成 | 保留失败日志，先恢复链路，再执行完整流程 | 最终完整实板流程通过，早期失败记录未覆盖 |
| Windows 探测脚本无法证明初始无视频 | 观察：第一轮启动时窗口尚未出现；后续探测开始时视频已打开 | 增加窗口等待，明确标记探测开始前的视频状态；启动无视频单独由 Qt 实板测试验证 | 不把探测前已有画面解释为自动开视频，不用失败的采样得出产品故障结论 |

## 5. 以后做项目要注意什么

1. 启动发现、控制连接、用户开视频、停止跟踪使用独立状态，不把“刷新”作为隐式开流按钮。

3. 测 UDP 握手时主动丢弃第一份回复，再检查重试、租约续期与过期会话拒绝是否都正确。
4. 验证无线链路时保留失败、恢复与复测记录；不要把第 05 份报告里当时未发现缺包的结论泛化到本次不同故障时段。
