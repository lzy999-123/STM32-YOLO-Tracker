## 2. 本次学到的知识

- 芯片 UART 与 STM32 编号独立 → STM32 USART2 对应本接线的 Luckfox UART2_M1，是核对引脚复用后的结果 → 不能仅凭两边都叫 UART2 进行配置。
- 调试控制台占用 → GPIO1_B2/B3 原来用于 ttyFIQ0，普通 serial 节点禁用 → 应同时核对设备树、console、earlycon 和普通 tty 节点。
- FIT 启动文件一致性 → 修改 DTB 后更新 data-size 与 SHA256，同时保留 kernel/resource → 可用于有明确备份和布局证据的设备配置维护。
- 小内存 Linux → 板子 Linux 可见内存约 33MB，额外 Python 模块和检查进程可能使视频被 OOM 结束 → 单参数解析不必加载 argparse/logging，纯标准库服务可使用 python3 -S。
- ACK 与机械运动的区别 → STM32 确认指令且模式变化，但两轴遥测均为 0、云台未接入 → 不能把通信成功写成运动成功。

## 3. 遇到的问题与解决过程

| 现象 | 证据与原因 | 处理方法 | 结果 |
| --- | --- | --- | --- |
| 按图接线却无应用串口 | 已确认：本地 RV1106 pinctrl 与板上 luckfox-config 均标明 B2/TX、B3/RX；引脚被 FIQ 控制台占用 | 备份后禁用 fiq-debugger、启用 serial@ff4c0000、移除 UART2 earlycon 并改用 console=tty0 | 重启后 ttyS2 指向 ff4c0000.serial |
| 首次准备写入的检查进程被 Killed | 观察：进程退出异常；整分区校验值仍等于原值。推断与低可用内存有关，未把未写入算作写入成功 | 改用 BusyBox 分块写入与流式 SHA256 校验，检查实际退出及读回结果 | 只更新前 38400 字节，整分区读回校验通过 |
| 视频进程被系统结束 | 已确认：dmesg 记录 rkipc 的 OOM；当时控制服务和维护进程共同运行。没有独立测量各进程对故障的因果贡献 | 去除 argparse/logging、采用 python3 -S、恢复视频并验证重启同时运行 | 后续重启检查未观察到新的 OOM，视频与控制同时运行；长期稳定性仍须观察 |
| 启动脚本可能留下失效 PID 且无日志 | 已确认：后台启动并不保证 Python 初始化成功，旧脚本缺少进程身份检查 | 检查 PID 对应脚本、启动后确认存活、停止等待、增加 status 与 /tmp 日志 | 实板 restart/status 及重启自动启动检查通过 |
| 指令 ACK 后角度始终为 0 | 观察：四方向、回中、跟踪相关命令均有 ACK，切换模式有真实遥测变化；用户确认云台未接入 | 将通信验收与运动验收分开，保留 STM32 原始角度，不在 UI 伪造角度变化 | 通信已确认，机械运动与角度闭环未确认 |

## 4. 验证与证据

- 修改前完整 boot：4194304 字节，SHA256 `4d4f934481b4f95191a89de205fe5fa706c970c674c82a72ceddbb3528bd98dc`。
- 修改后完整 boot 读回：SHA256 `6968ebe4528e2346169b998d53b41c559e2368108c589279619a680104b3dd2e`。
- 修改后的 DTB：SHA256 `9398f07e1a0595bafd08d0581c6731649a3a9626604161dcb258c070c95a6689`；FIT 中大小、hash 同步更新。
- 主机按字节确认 `0x9600` 起的内核与资源内容不变；板端完整分区读回与准备文件一致。
- 完整备份在忽略的 `tmp/uart2-backup-20261008/`；板端保留原启动前缀。曾部署重启未确认时自动恢复的临时脚本，验证成功后已移除其开机入口。
- 实体被动 UART 检查：5 秒收到 520 字节、52 帧 type 0x81 遥测，帧 CRC 检查通过；mode=0、两轴角度=0。记录在 `tmp/uart2-passive-result.txt`。
- 实体生产 UDP 5005：四方向、回中、模式切换、跟踪开始/停止均有实际 UART ACK；模式 0→1→0 回传通过。重复同一 request 获得缓存 ACK；因角度一直为 0，没有据此声称实体步进次数验收成功。
- 短时发送负目标偏移、客户端停止心跳后重新握手均成功，记录在 `tmp/wireless-real-control-summary.json`。重新握手时角度为 0 不能证明真实回中运动或机械失控保护已通过。
- 真实 Qt UI：无线视频实际显示，状态栏显示 STM32 在线；点击模式切换后实际遥测驱动“手动/自动”标签变化，自动模式的四方向禁用。诊断截图仅在忽略目录保存。
- 精简模块后重新运行 Python 桥接行为测试：10 项通过；Qt Release 构建、两项 Qt 行为测试及软件隔离实板测试证据见第 03 份报告。
- 最后重启：ttyS2、RTSP 554、控制 5005、发现 39093 恢复；无需手工启动服务即获得 online=true 的 STM32 遥测。记录在 `tmp/uart2-reboot-control-result.json`。
- 最后重启约 3 分钟时，rkipc 与控制服务同时运行，dmesg 未出现新的 OOM；可用内存约 4MB。`sh -n` 启动脚本检查通过。没有将短时观察写成长期稳定性保证。
- Designer 视频区域核对为 832×468，严格满足 16:9；qmake 项目无 serialport/serialcontroller 引用。`git diff --check` 通过。
- 没有执行同步端到端延迟测量，也没有验证实体舵机运动。

## 5. 以后做项目要注意什么

- 接线图必须落实到芯片 pinctrl 的 TX/RX 功能，交叉接线并共地；修改默认控制台前保留远程管理和对应备份。
- 修改 FIT 时同时核对 DTB 和头部元数据，不能只替换原始 DTB；写入后必须读回检查。
- 设备内存有限时，流式检查优于同时读取多份完整固件；维护进程本身也要计入资源开销。
- 服务 PID 文件不是成功证据，应检查对应进程、监听端口、实际遥测及重启后的自动恢复。
- 在没有机械负载时可完成通信验收，但运动、真实角度与物理停止必须留到完整硬件状态下验证。

## 6. 当前不足与下一步

- 用户接入云台及相应供电后，验收方向、0.5° 步进、回中、目标跟踪与角度反馈；若反馈仍不符合预期，再核对 STM32 固件和 PWM 输出。
- 在实际运动期间测试断网停止、重连不恢复旧目标，以及 STM32 自身链路保护。
- 无线视频仍有现场解码告警和帧率波动；继续区分网络/解码指标与真正的端到端延迟。
- 小内存板子的长期同时运行稳定性尚待实物使用观察，不能将本次短时测试替代持续验收。
