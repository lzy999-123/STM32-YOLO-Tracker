## 2. 本次学到的知识

- 软件检查与 UART / 屏幕确认递进 → 新固件发能力声明、桥接读取真实关联、用户看到名称三段证据分别核对 → 可复用到其他下位机信息页。
- 小内存设备采用串行替换 → 停止旧桥接后可用内存从约 5.6 MiB 增到约 9.9 MiB，再启动新版 → 避免维护时叠加多个完整 Python 进程；这不能单独证明首次超时由内存造成。
- 诊断日志应保留状态而不保留网络名称 → 输出能力版本、状态码和 SSID 字节数 → 可验证新增上报已启用，同时避免名称及凭据进入长期记录。
- 部署中断要定位到具体阶段 → 原脚本、备份和候选文件分别校验 → 重启恢复后能够确认实际仍在运行哪个版本。

## 3. 遇到的问题与解决过程

| 现象 | 证据与原因 | 处理方法 | 结果 |
| --- | --- | --- | --- |
| 首次额外探测没有返回 | 旧脚本备份与候选 MD5 已核对，但额外 Python 探测超时；之后 SSH banner 与视频端口也超时；没有取得该次板端故障日志，根因未知 | 用户重新上电，重新发现和核对三个脚本；停止旧进程后替换并启动新版 | SSH / 控制 / 发现 / 视频服务响应恢复 |
| 原日志无法证明新元数据已启用 | 只有普通 UART 打开与控制服务记录 | 新增能力声明日志与 Wi-Fi 状态 / 字节数变化日志，不记录名称内容 | 实际收到能力版本 1，并上报已连接状态及 10 字节名称 |
| 仅有软件日志仍不足以确认 OLED | UART 能力及桥接状态无法代替屏幕观察 | 请求用户短按 PC13 查看 | 用户确认“名称显示正确” |

## 5. 以后做项目要注意什么

1. 替换前保留旧脚本和校验值，上传候选后再停止服务并替换。
2. 小内存设备尽量只运行一个完整桥接 Python 进程；维护诊断优先复用现有日志与 shell 工具。
3. SSH 超时不直接归因为 OOM 或 Wi-Fi 驱动故障；没有当次日志时保留未知结论。
4. 显示功能至少核对运行状态来源、实际 UART 能力及用户屏幕观察。
