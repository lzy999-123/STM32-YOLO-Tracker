## 1. 本次目标与完成情况

用户明确要求原生720p、连续稳定30个不同画面/秒，不接受15/45的平均30；延迟优先控制在300ms内。

已完成并通过构建/回归的实现：

1. 以原生 FFmpeg 替换 RTSP 的 OpenCV 收流循环，每个解码器持有自己的连接参数和可取消期限；保留源 PTS、序号、关键帧及损坏统计，验证1280×720和可用的源帧率元数据。
2. 使用单调时钟和源时间戳生成30Hz播放期限，默认150ms、有界24帧队列；不重复旧帧、不突发追帧，分别记录缺失、迟到、重复和溢出。
3. 显示与跟踪分开：最新解码帧驱动后台跟踪，缓冲显示帧不触发跟踪；相对接收积压超过200ms时不使用该输入。
4. 维持旧会话取消、有限重连、安装方向和左上角时间；异常时清除旧画面、旧跟踪输入和旧FPS。
5. 新增直接使用正式源码/窗口的时序探针与分析器，同时检查源身份和Qt绘制；新增拒绝平均30和重复绘制旧帧的分析回归。
6. 板端由Baseline/768kbps试验为High/1024kbps，保持720p30/GOP15；已保存原配置备份。电脑和板子切至手机热点做实际对照，视频优先级继续保持默认。

**未达到连续稳定30帧的实机验收。** 手机热点曾连续44个完整秒均绘制30帧，随后仍断流；TCP对照也失败。没有同步光学证据，不宣称端到端延迟已经低于300ms。正式程序已备份并更新，后续实机完整启动验证仍有失败。

## 2. 本次学到的知识

- 源时间戳与到达时间不同 → 网络暂停后仍可突发到达大量源帧 → 播放按源PTS排期限，跟踪取最新输入。
- 固定播放节奏不能制造缺失画面 → 有限150ms缓冲无法填平一秒空档 → 缺帧必须单独统计，不拿重复帧填到30。
- 图像质量包含解码完整性和颜色范围 → UDP损坏后等待关键帧，YUVJ420P按全范围转换并复用swscale上下文 → 避免花屏和重复颜色转换初始化。
- 每个连接独立参数可避免全局环境变量污染 → `AVFormatContext`内部维护传输/探测/取消参数 → 多会话取消和重连时不改进程全局配置。
- 系统连接成功不等于保持同一网络 → Windows曾在热点测试中切回实验室5GHz网络 → 将这些启动失败与有效性能窗口分开。
- Qt提交画面不等于真正绘制 → 同时记录源身份和Paint事件 → 识别平均帧率、重复重绘和GUI合并丢帧。

## 5. 以后做项目要注意什么

1. 同时检查每秒不同源画面、源PTS间隔、实际绘制和最长空档；平均FPS只作为辅助统计。
2. 健康短窗口后必须持续测试；出现恢复即判本轮连续性不通过。
3. 低内存板子减少诊断进程，避免媒体客户端与多个管理连接叠加；记录诊断本身引入的压力。
4. 改网络前后确认实际SSID和IP；连接请求成功与保持连接分别检查。
5. 播放延迟与跟踪输入分离，但相对接收积压不能替代同步光学延迟。
6. 备份配置和EXE，保留失败试验，不靠提高缓冲到秒级或降低原生规格绕过用户约束。
