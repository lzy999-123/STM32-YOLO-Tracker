## 2. 本次学到的知识

- 平均帧率与均匀到帧不同 → 本次约 30 FPS 的视频仍出现约 0.34～0.41 秒到帧停顿 → 实时视频需同时检查平均值、间隔和突发到达。
- 缩小故障范围 → 原始 RTP 不经过 OpenCV 解码、Qt GUI 或 YOLO，同样出现停顿 → 可以排除这些消费者是当前全部卡顿的唯一来源。
- 相关性与因果不同 → 新控制服务增加板端内存占用，但停掉后相近抖动仍存在 → 不能仅凭“增加通信后卡”断言通信直接阻塞视频。
- 环境参数必须到达实际插件 → 首轮 Python 使用 os.environ 后仍有约五秒探测，后续同步 msvcrt 环境，开流降为约 568ms → 另一套 Python 的默认行为不能直接代表 Qt 参数生效情况。
- 图像时序指标的边界 → RTP 时间戳增量约 33ms，但实际接收间隔能达数百毫秒 → 时间戳反映媒体时序，不能直接证明摄像头物理采集规律或摄像头到屏幕延迟。

## 5. 以后做项目要注意什么

- 回归验收要在视频、控制和发现同时运行时检查到帧间隔，保留相同网络和场景条件的基线。
- 不用界面FPS显示或平均解码帧率替代“画面流畅”与延迟验收。
- Pico Plus的内存余量有限，新增常驻Python服务应同时记录RSS、可用内存和持续视频表现。
- 临时暂停控制服务后必须恢复，并核对实际进程；独立测试不能重放旧坐标或用户命令。
- 最新帧覆盖可避免消费者积压，但不能补出网络尚未送达的画面；引入平滑缓冲需要另行评估额外等待与跟踪控制需求。
