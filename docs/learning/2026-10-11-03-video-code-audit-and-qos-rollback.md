## 1. 本次目标与完成情况

用户认为实验室网络下的卡顿可能来自视频传输代码，要求从发送到显示完整检查，并对比 GitHub 历史。实际检查了摄像头/ISP/编码计数、厂商 RTSP 调用、套接字优先级、RTSP 参数、OpenCV FFmpeg 后端、取帧循环、会话取消/重连、GUI 最新帧分发和后台跟踪。GitHub 实时核对最新 `master` 仍为上述基线，历史 `ecd73bf` 的视频文件 blob SHA 与本地 Git 一致。

本次纠正 [前份传输修复报告](2026-10-11-01-video-stutter-transport-recovery.md) 中的 AF41 默认策略：设置成功不能说明链路性能改善。两轮同一旧版 UDP 收流代码的实板对照，强制 AF41 均明显差于默认优先级。旧 `ecd73bf` 在当前板端设置下也会卡，不能据此排除后来部署的板端代码，也不能仅回滚上位机。

已完成的代码修复：

1. `S99zzzvideoqos` 默认关闭 AF41；没有 `/userdata/cfg/enable-video-qos` 标记时停止检查进程并恢复现有套接字默认优先级。下次启动也保持默认策略。`stop` 同时撤销现有套接字的 AF41 设置，避免仅停止进程却保留 TOS；启用标记文件需单独删除，才能保证下次启动仍关闭。
2. 播放中读取/解码失败时，下一次恢复尝试另一传输；记录实际打开的传输方式，保持关闭/切流取消和有限恢复预算。单种传输打开等待上限由 5 秒改为 2.5 秒。
3. 画面写入、会话核对和 GUI 通知登记放入同一把锁。原代码解锁后再 CAS 登记，可能在关闭/重连清零之后被旧 worker 重新置为 pending，旧通知又因会话失效提前返回，进而挡住新会话通知。此项是代码审查确认的可达竞态，未宣称它就是本次每一次卡顿的触发点。

上位机 Release 已部署至原运行目录。板端新启动脚本已部署、`sh -n` 通过，实际报告 disabled，无视频优先级常驻进程。脚本 LF 内容 SHA256 为 `fe96666a66fa9afa09758c9e102f29f27a8026d2885e52986a4d0a196779a509`，与板端读回一致。没有重启板子，也没有执行实体电机运动。

## 2. 本次学到的知识

- 历史回滚要覆盖发送端 → 旧上位机在新 AF41 板端仍只有 7.77 FPS → 网络链路审查不能只换 PC EXE。
- DSCP/WMM 的实际效果需对照 → 旧版 UDP 的两轮默认优先级均达到约 25～27 FPS，AF41 约 8～11 FPS → 优先级应在目标 AP/驱动组合验证后才启用。
- UDP 发送失败发生在接收端之前 → 内核 `SndbufErrors` 与 IP 丢弃计数增加 → 不能把缺包都归为电脑解码慢。Linux 5.10 中该指标同时涉及内核内存和发送缓冲，不能仅凭指标就认定需要加大 SO_SNDBUF。
- 最新帧通知也需要会话同步 → 帧锁之外的 pending CAS 可被旧线程抢占 → 将会话作废、画面发布和通知登记作为同一同步边界。
- 诊断也会消耗板端内存 → 部署期间出现 OOM，`rkipc` 被内核终止 → 对约 33 MB 可管理内存的设备减少同时维护连接和临时 shell，记录诊断引入的压力。

## 3. 遇到的问题与解决过程

| 现象 | 证据与原因 | 处理方法 | 结果 |
| --- | --- | --- | --- |
| 认为换实验室网络后是 PC 收流代码退化 | 同链路历史 `ecd73bf`、当前 UDP 和当前 TCP 均出现低 FPS/长空档 | 单客户端、同参数、依次对照，保留旧代码快照 | 排除简单回滚 PC 就能恢复的结论 |
| AF41 可能造成不同队列行为 | 两轮旧 UDP 的开关优先级对照；驱动来源中的 `ip_hdr.tos >> 5` | 临时恢复默认后测试、再恢复 AF41 反向验证 | 有重复性能退化证据；具体 AP/驱动内部机制仍未唯一定位 |
| 播放损坏仍重开 UDP | 当前策略只在 open 失败回退；读取失败重新进入 UDP 优先 | 恢复时切换传输，健康连接保持当前传输 | 新增回归覆盖传输选择及预算 |
| 切流后后台有帧却可能不通知 | 原锁外 CAS 与 stop 清零/旧会话通知存在竞态 | 统一帧锁范围，旧发布与旧通知不得消费新会话状态 | 新增会话隔离回归通过 |
| 维护连接握手变慢，后续无视频 | 部署诊断期间 `sh` 触发 OOM，内核在 uptime 2147.80 秒杀掉 PID291 `rkipc` | 保留内核记录；固定 SSH 主机公钥重新接入；恢复同配置摄像头 | 摄像头恢复为 PID1717；不把此次诊断期间 OOM 当作最初截图卡顿的已证原因 |
| 板端脚本哈希首次不一致 | here-document 额外写入一个末尾换行 | 重新部署精确 LF 内容，读回比较 | SHA256 相同；正常策略报告 disabled |

## 5. 以后做项目要注意什么

1. 对照 PC 历史代码时固定并记录板端代码、固件、套接字设置和视频参数；板端新增设置同样能使历史 EXE 变差。
2. QoS 应默认保留系统策略，依据每种链路的开/关对照启用；停止服务要撤销已有套接字设置。
3. 对故障恢复检查正在播放后的质量与传输选择，不能只检查 RTSP 握手成功。
4. 小内存设备诊断优先一个复用维护连接；部署前注意内存和遗留连接，诊断期间发生故障必须恢复并诚实记录。
5. 同时报告最大间隔、长空档次数、解码与绘制节奏；这些数值不等于摄像头到屏幕的同步端到端延迟。

## 6. 当前不足与下一步
