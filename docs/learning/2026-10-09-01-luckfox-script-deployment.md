## 2. 本次学到的知识

- **启动脚本升级涉及进程归属变化** → 旧PID记录Python进程，新PID记录守护外壳 → 覆盖前先使用旧脚本停止服务，再备份、部署，避免旧进程继续占用端口。
- **进程检查应匹配可执行脚本** → 发现服务参数也包含`luckfox-control.json`，宽泛搜索会误判控制服务残留 → 检查停止结果时匹配`/oem/usr/bin/luckfox-control.py`完整路径。
- **重启成功需要运行证据** → ADB返回成功后，再核对启动标识变化、服务状态、端口和UART打开日志 → 可复用于设备部署后的自启验收。
- **编译成功与运行依赖完整是两项检查** → 新Release目录最初缺少ONNX Runtime和Qt运行库 → 按构建使用的版本准备DLL及插件，再开展界面联调。

## 3. 遇到的问题与解决过程

| 现象 | 证据与原因 | 处理方法 | 结果 |
| --- | --- | --- | --- |
| 最初有线ADB连接失败 | 观察：连接超时；后续Windows显示以太网`Disconnected`、链路速率0，USB ADB设备列表为空。未据此认定板子故障 | 使用已保存的无线地址；用户恢复板子和电脑连接同一热点后重新连接 | 无线ADB连接恢复，未扫描网段 |
| 本地备份校验辅助程序首次报`IndexError` | 已确认：ADB输出行间空行，被本地解析器当作哈希记录 | 跳过空行，重新读取现有备份校验；没有重复覆盖备份 | 四个备份文件与原文件MD5一致 |
| 停止测试误报控制进程残留 | 已确认：唯一匹配行是发现服务，其配置参数含`luckfox-control.json` | 用控制Python脚本完整路径复核，再重新启动控制服务 | 控制服务停止后无匹配进程，重新启动成功 |
| 重启后日志日期为1970年 | 观察：重启后的服务日志以`1970-01-01`开头；本次未调整板端时钟 | 用启动标识变化、运行时长和真实进程验证重启，不以日志日期作为墙钟时间证据 | 重启与自启得到验证；时钟同步未验收 |
| 联调程序目录缺少运行库 | 观察：初始目录无ONNX Runtime及Qt DLL；构建文件使用ONNX Runtime 1.20.1、Qt 6.10.1 | 从现有1.20.1目录复制四个ONNX Runtime DLL并核对SHA256；运行对应Qt的`windeployqt` | 文件准备完成；界面操作仍未执行 |

## 5. 以后做项目要注意什么

1. 部署按停止旧服务、备份、覆盖、校验、启动、功能验证顺序执行；已有备份先核对，避免把旧版本覆盖掉。
2. ADB输出按真实字符编码处理并过滤空行；本地解析异常与板端命令失败分别记录。
3. 进程匹配依据完整脚本路径，避免配置文件名造成误判。
4. 重启必须取得用户授权，检查启动标识变化后再判断自启通过；断线本身不证明重启完成。
5. 每一轮都核对受保护配置的校验值；日志先检查是否含密钥，再展示或归档。
